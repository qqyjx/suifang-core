SSH 免密（首次配置）

服务器 /root/.ssh/authorized_keys 里放着若干台机器的公钥，配过的机器可以免密 SSH。 Windows 主机和 WSL 是两台不同的机器、两把不同的 key（C:\Users\<你>\.ssh\ 和 WSL 的 ~/.ssh/ 互不相干），要各推各的——2026-08-02 之前只有 Windows 那把在里面， 这就是当时 WSL 里 ssh 报 Permission denied (publickey) 的全部原因， 和 WSL 的网络能力无关。

新机器接入步骤：

# Windows
ssh-keygen -t ed25519                                   # 生成 key
ssh-copy-id root@192.168.4.104                          # 推上去（要密码 8ik,(OL>）
# 之后 ssh root@192.168.4.104 不再问密码

启动服务

服务由 systemd 管理：

systemctl status suifang     # 查看状态
systemctl restart suifang    # 重启
systemctl stop suifang       # 停止
systemctl start suifang      # 启动
journalctl -u suifang -f     # 看实时日志

重启后自动恢复（Restart=on-failure + WantedBy=multi-user.target）。

关键坑（写在 scripts/suifang.service 注释里）

坑 1：必须用 miniconda 的 Python，不能用系统 python3

  • /usr/bin/python3 是 3.6，没装 pymysql
  • /root/miniconda3/bin/python3 是 3.8，装了 pymysql 1.4.6
  • systemd 不加载 root 用户的 PATH，所以 ExecStart=python3 ... 会找系统 python，启动失败
  • 解决：ExecStart 写绝对路径 /root/miniconda3/bin/python3

坑 2：CentOS 7 systemd 219 不支持 StandardOutput=append:/...

  • append:/path 语法是 systemd 240+ 才有
  • CentOS 7 systemd 219 会静默忽略这一行（不报错，但日志不写）
  • 解决：用 /bin/sh -c '... >> log 2>&1' 包一层做重定向
  • 注意要 exec 替换 shell 进程，否则 systemd 管理的是 sh 而不是 python

最终 unit 文件见 scripts/suifang.service。

2026-08-02 更新：上面这段"WSL 连不上"的旧说法已经不成立。 现在公司 VPN 连上之后，WSL 这边 ping 192.168.4.104 和 22 端口都是通的， 实测能完成 SSH 握手。当年那条结论（WSL2 不共享 Windows VPN tunnel）大概率是 VPN 客户端配置变过，或者 WSL 网络模式改过。

WSL 里如果还连不上，先分清是网络还是认证——这两件事 的报错完全不同，别再一律归到"WSL 网络限制"上：

  • Connection timed out / ping 不通 → 真的是网络，检查 VPN 是否连着。
  • Permission denied (publickey) → 网络是通的，只是这台机器的公钥不在服务器 ~/.ssh/authorized_keys 里。按上面「SSH 免密（首次配置）」推一次公钥即可， WSL 和 Windows 是两把不同的 key，各推各的。
  • 连上去却发现是别的机器 → 检查 ~/.ssh/config。历史上为了走隧道加过一条 Host 192.168.4.104 / HostName 127.0.0.1 / Port 2222 的别名，VPN 直连之后 这条只会帮倒忙，会把 ssh root@192.168.4.104 悄悄拐到本地 2222 端口。 临时绕开用 ssh -F /dev/null -i ~/.ssh/id_ed25519 root@192.168.4.104， 长期建议直接把那段别名删掉。

所以部署在 Windows（Git Bash）还是 WSL 里跑都可以，条件只有一个：那台机器的公钥 已经推上去了。
