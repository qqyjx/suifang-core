◎总览

采集层已建成在产,平台层空缺 — 本方案把"1.0 落地四步"落成可评审的设计。

现状:三条设备数据链路(S101/R04 小程序、诊脉仪浏览器上传、iwown 4G 直传)均已上线生产,数据入六元 MySQL(h6dp_suifang),但目前只有"按设备看数据"的三块独立看板,没有以患者为中心的随访平台层 — 患者绑定、跨设备患者视图、报警工作台、佩戴依从性统计都还不存在。

本方案定义:随访平台 1.0 的定位边界、总体架构、5 个功能模块、3 张新增数据表、8 个新 API、3 个前端视图、4 个里程碑。评审通过后按 ⑦ 里程碑推进,产出一个接真实生产数据的可用版本,直接进入生产试点。

①定位与边界

平台是什么、按什么原则建,以及 1.0 明确不做什么。

1.1 定位:自建随访平台

平台由我方自建自用:三条设备链路已经在我方手里跑通并在产,患者绑定、跨设备患者视图、报警闭环、依从性统计在同一套栈上顺势建成,即为一个完整可用的随访平台 1.0。核心是把"采数据"升级为"以患者为中心的随访工作流"— 医护打开一个页面,能看到每个患者是谁、体征怎么样、有没有报警、报警处理到哪一步。

1.2 设计原则

原则含义
零新依赖服务端只扩展现有 health_server.py(Python 标准库 + pymysql,CentOS 7 可跑);前端为静态 HTML/JS,GitHub Pages 或 .104 均可托管
不动生产 schema现有 6 张生产表(wearable_device* / zhenmaiyi / iwown_* / ble_event)一列不改,平台层只新增 platform_* 前缀表
复用生产链路外网入口沿用 dc.ncrc.org.cn/api2 反代,不新开域名/端口
以门诊号为患者主键与 S101 现行"门诊号"体系同构,iwown 的 iwown_device.patient_no 字段已预留,天然打通

1.3 非目标(1.0 不做)

  • 不做 HIS/电子病历系统对接,不做完整 EMR — 2.0 再议
  • 不做随访计划/问卷引擎(排期到 1.1,本方案仅预留数据模型钩子,见 3.5)
  • 不做账号权限体系 — 原型阶段沿用现看板的"链接即访问"模式,上生产前再加最简 token 门
  • 不做 App / 小程序新端 — 平台是医护侧 Web,患者侧维持现状

②总体架构

在已在产的"采集层 + 存储层"之上,加一层平台服务(API 扩展)和一层平台前端。

┌────────────────── 采集层(已在产,不改) ──────────────────┐
│ S101/R04 ─BLE→ 微信小程序 ─┐                              │
│ 诊脉仪 ─导出zip→ 浏览器解析 ─┼─HTTPS→ dc.ncrc.org.cn/api2 ─→ :3000 health_server.py │

│ 新增:platform_patient / platform_alarm / platform_followup_log   ← 本方案 ④     │
└──────────────────────────────────────────────────────────┘
                              ↑ 读写
┌────────────────── 平台服务层(本方案 ⑤) ──────────────────┐

为什么挂在 health_server.py 而不是新进程:平台 API 是低频 JSON 读写,与现有 /api/data 同型;单进程省一套 systemd/反代/运维文档。iwown 的报警帧解析已在 iwown_server.py 落库(data_type='alarm'),平台层只做读取+视图,不碰二进制链路。

③功能模块

1.0 四个实做模块 + 一个预留钩子,对应调研报告"1.0 落地四步"。

3.1 M1 患者中心(患者绑定)

建统一患者索引 platform_patient(门诊号为业务主键),后台页面把三条链路的设备归到患者名下:

链路绑定方式现状
iwown 4G写 iwown_device.patient_no(字段已预留)待做 后台绑定页
S101/R04门诊号已写入大 JSON 每条记录,按 patientNo 过滤即归户已通 复用现逻辑
诊脉仪zhenmaiyi.case_id ↔ 门诊号映射,录入时对照待做 映射维护

3.2 M2 患者视图(跨设备体征趋势)

单患者页聚合三链路数据:心率 / 血氧 / 血压 / 体温 / 步数五类核心体征按天趋势图(iwown 分钟级取日聚合,S101 按记录),脉诊结果卡片(诊脉仪),设备状态条(电量/在线/最近上传)。三块现有看板的图表方案直接复用,只是把"按设备"翻转成"按患者"。

3.3 M3 报警工作台(采数据 → 主动干预)

iwown 0x12 报警帧(跌倒 / SOS 含定位 / 心率血氧血压体温越限 / 久坐 / 未佩戴 / 低电量)已由 iwown_server.py 无损落库(iwown_data.data_type='alarm')。平台层做三件事:

  • 事件化:定时/触发式把 alarm 行解析进 platform_alarm 事件表(类型/等级/定位/原始引用)
  • 工作台:报警列表按状态过滤,CRC 点开处理 → 记录回访结果
  • 闭环状态机:new → acked(已知晓) → followed(已回访) → closed,每步落 platform_followup_log,可审计

3.4 M4 佩戴依从性

用"未佩戴报警 + status 帧在线/电量"计算每患者每日佩戴率,患者列表卡片上直接显示,作为随访质量指标。纯查询视图,不新增表。

3.5 M5 随访计划(1.1 预留,不实做)

计划/任务/问卷引擎推迟到 1.1。1.0 仅在 platform_followup_log 里预留 plan_id 空列作为钩子,避免将来迁移改表。

④数据模型

只新增 3 张 platform_* 表,现有表一列不改。

表用途关键字段
platform_patient 患者主索引 patient_no(PK,门诊号) / name / gender / age / group_tag(队列/分组) / zhenmaiyi_case_id(诊脉仪映射) / note / created_at
platform_alarm 报警事件(由 iwown_data alarm 行解析而来) id / patient_no / device_id / alarm_type(fall/sos/hr/spo2/bp/temp/sedentary/not_worn/low_battery) / severity(crit/warn/info) / lat,lng(SOS 定位) / payload_json / source_data_id(→iwown_data.id,可回溯) / status(new/acked/followed/closed) / occurred_at
platform_followup_log 回访/处理记录(报警闭环 + 日常随访通用) id / patient_no / alarm_id(可空,日常随访无报警) / action(ack/call/visit/note/close) / result_text / operator / plan_id(1.1 钩子,暂空) / created_at
去重与幂等:platform_alarm.source_data_id 加唯一索引,解析任务重跑不会产生重复事件;原始帧仍在 iwown_data.raw_hex,任何字段疑义可重放验证。DDL 与现有做法一致,由服务启动时 ensure_tables 幂等创建,同时归档到 database/platform.sql。

⑤API 设计

扩展 health_server.py,统一 /api/platform/* 前缀,经 dc.ncrc.org.cn/api2 反代直接可用。

方法路径用途服务模块
GET/api/platform/patients患者列表 + 各链路设备绑定态 + 最近上传时间 + 佩戴率M1/M4
POST/api/platform/patientUPSERT 患者(建档/改档)M1
POST/api/platform/bind绑定/解绑:{patient_no, chain: iwown|s101|zhenmaiyi, key}M1
GET/api/platform/patient/vitals?patientNo=&days=单患者跨链路体征日聚合(五类核心体征 + 脉诊卡)M2
GET/api/platform/alarms?status=&patientNo=报警工作台列表M3
POST/api/platform/alarm/transition报警状态流转 {alarm_id, action, result_text, operator}M3
POST/api/platform/alarm/ingest触发一次 alarm 行 → 事件表解析(幂等,供定时任务/手动刷新)M3
GET/api/platform/compliance?patientNo=&days=佩戴依从性明细(每日佩戴率曲线)M4
写接口的最简门禁:原型阶段读接口开放(与现看板一致),POST 写接口要求 header 带共享 token(环境变量注入,不入仓),防止公网误写。1.1 再升级为账号体系。

⑥页面设计

单文件 prototype/platform.html,三视图切换,与现有三看板同一工程习惯。

视图内容交互
患者列表(首页)患者卡片:姓名/门诊号/分组、三链路绑定徽标、最近体征摘要、佩戴率环、未处理报警角标点卡片进详情;顶部"+建档/绑定"入口(M1 后台功能就近放这里)
患者详情五类体征趋势图(7/14/30 天切换)、脉诊结果卡、设备状态条、该患者报警时间线图表方案复用 iwown-dashboard 现有实现
报警工作台报警列表(状态 tab:待处理/已知晓/已回访/已关闭),行内显示类型/等级/患者/时间/定位点行弹处理框:知晓 / 记录回访结果 / 关闭,落 followup_log

⑧风险与待确认

事项风险/未知动作
报警帧真机验证0x12 协议已支持、落库链路已通,但跌倒/SOS/越限各子类型尚无真机样本回归M2 验收即真机触发;raw_hex 全存,可重放
